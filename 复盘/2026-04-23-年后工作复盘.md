# 年后工作复盘

## 一、开年以来的项目开展情况

开年以来，我的工作重点主要集中在数据接入、数仓加工、BI 看板支撑和新需求承接这几条主线上，整体推进节奏比较连续。

1. 前期主要完成了沃尔玛、Shopee、TikTok 等平台接口的对接与调试，逐步把订单、产品等数据接入进来，为后续数仓加工和看板分析打基础。
2. 3 月开始，重点投入 TK 看板相关需求，先后完成了需求确认、表结构设计、接口开发、数仓逻辑实现、前后端联调和问题修复，推动项目逐步落地。
3. 4 月重点推进了 PID 看板相关需求，完成了 PID、广告、视频挂车、开单视频等数据的整合与分析，支撑商品和经营分析场景。
4. 在完成前期需求交付的同时，也开始承接库存、缺补货、TK 审核等后续需求，工作逐步从单项开发转向持续性的 BI 和数仓支撑。

整体来看，年后这段时间的工作已经从“把数据接进来”，逐步走向“把数据做成可分析、可支撑业务决策的能力”。

## 二、这两个多月遇到的问题及解决方案

这段时间遇到的问题，主要集中在以下几个方面：

1. 数据口径不一致。
   不同来源的数据在订单状态、退款逻辑、GMV、订单量等方面存在差异，导致结果难以直接对齐。针对这类问题，主要通过拆分来源、逐项核对字段和口径、推动业务确认规则的方式来解决。

2. 外部平台接口复杂，调试成本较高。
   不同平台在授权、token、字段定义和同步机制上差异较大。针对这类问题，主要是优先验证高风险环节，先跑通最小闭环，再逐步扩展完整链路，同时增加重试和告警机制，提高稳定性。

3. 历史数据和增量处理容易遗漏。
   在处理历史数据、补数和日常增量时，出现过数据遗漏和时间窗口覆盖不全的问题。对此主要通过补充历史回灌方案、明确时间窗口和重跑策略来降低风险。

4. PID 与 SPU 关系缺少稳定规则。
   这部分对商品维度分析影响比较大，当前主要通过维表维护和人工补充映射的方式，先保证看板可用，再逐步优化规则。

总体来说，这段时间很多问题并不只是技术实现问题，更是业务口径、数据来源和系统现状共同作用的结果，所以解决思路也更多是“技术处理 + 沟通确认”并行推进。

## 三、工作与学习心得

经过这两个多月的工作，我有三点比较深的体会：

1. 做数仓和 BI，最重要的不是先写 SQL，而是先把指标口径和业务规则弄清楚。只有口径统一了，后面的开发和核对才会更顺。
2. 数据工作不能长期依赖临时排查，后续需要继续加强指标口径、调试方法和维表规则的沉淀，提高交付效率和稳定性。
3. 在保证需求交付速度的同时，也要兼顾后续可维护性，尽量把关键逻辑沉淀成标准化能力，而不是每次都重复处理同类问题。
4. 从这段时间的实际情况来看，业务需求在最开始往往很难一次性定义完整，这其实是正常现象。很多指标口径、使用方式和展示细节，只有在第一版真正上线、业务实际使用之后，问题才会逐步暴露出来。对我来说，一个比较深的体会是，需求第一版要尽快上线，先让业务用起来，再根据真实反馈持续调整。因为如果第一版迟迟不上线，很多内容都停留在口头沟通阶段，业务理解和技术理解之间的差异其实很难真正暴露和统一。

另外，这段时间也让我更深地体会到，数据仓库和 BI 工作不仅是开发实现，还需要主动推动需求确认、口径统一和问题闭环，只有这样，数据结果才能真正支撑业务。

## 四、小结

总体来看，年后到现在，我的工作重点已经逐步从接口接入和基础数据处理，转向看板建设、指标实现和业务分析支撑。虽然过程中遇到了口径不一致、接口复杂、历史数据处理和维度治理等问题，但也积累了更成熟的处理思路。

后续我会继续在数仓和 BI 方向上，加强数据标准化、口径沉淀和稳定性建设，更好支撑业务需求落地。

# 年后工作复盘（详细版）

## 一、开年以来的项目开展情况

结合 2026 年 2 月到 2026 年 4 月的工作情况来看，年后整体工作的推进大致可以分为四条主线：一是外部平台接口对接和数据接入，二是 TK 看板相关需求建设，三是 PID 看板和商品分析能力建设，四是库存、缺补货等后续需求承接。整体节奏上是比较连续的，重点也逐步从“把数据接进来”转向“把数据做成可以支撑分析和决策的产品能力”。

### 1. 外部平台接口对接与基础数据接入

年后初期，主要围绕沃尔玛、Shopee、TikTok 等平台开展接口对接与调试工作，逐步完成订单、产品、token、授权等相关能力接入。这部分工作的重点，表面上看是把接口调通，但实际上更重要的是把不同平台的数据源逐步沉淀为后续数仓和 BI 可以稳定使用的数据基础。

在这个阶段，除了完成接口开发外，也同步开展了数据核对、流程调试和异常问题排查。通过这一阶段的工作，对不同平台在授权方式、字段定义、同步逻辑和异常场景上的差异有了更深入的理解，也为后面做统一分析、统一加工打下了基础。

### 2. TK 看板需求从确认到落地

3 月开始，工作重心逐步转向 TK 看板相关需求。前期主要集中在需求确认、原型调整、UI 细节沟通、技术方案拆解和排期评估，之后进入表结构设计、接口详细设计、数仓抽取与计算逻辑开发，再到前后端联调、问题修复和上线准备。

从整个推进过程来看，这部分工作已经比较完整地经历了需求、设计、开发、联调和交付的全过程。过程中不只是完成了后端开发，也做了较多与指标口径、表结构设计、前后端配合相关的工作。尤其是商品统计、店铺统计和相关 RPA 数据支持这几块，说明项目本身并不是单点开发，而是已经在向更系统化的数据产品建设推进。

### 3. PID 看板与商品维度分析建设

4 月重点推进了 PID 看板相关需求，涉及 PID 模块、广告模块、视频挂车、开单视频、商品统计发送图片，以及 PID 与 SPU 的映射处理等内容。这部分工作相比前期接口接入，更偏向数仓和 BI 的核心能力建设，需要同时处理数据来源、指标融合、粒度统一和维度映射等问题。

这项工作的价值在于，逐步围绕“店铺 + PID”这一核心粒度，补齐商品分析、广告投放、视频表现等多个分析视角，使数据不仅能展示结果，还能支撑更细粒度的经营分析。从工作内容来看，这部分已经不只是做数据接入，而是在做真正有业务价值的数据分析能力沉淀。

### 4. 后续需求的持续承接

在推进前述需求的同时，也逐步开始承接库存、缺补货、TK 审核等新的业务需求。这说明当前工作已经进入一种持续交付状态，不是做完一个项目就结束，而是边支撑现有系统稳定运行，边承接新的数据与分析需求。

总体来看，年后这段时间的项目推进有几个比较明显的特点：

1. 从接口接入逐步走向数仓加工和指标建设。
2. 从单点功能开发逐步走向完整需求链路交付。
3. 从“数据可拿到”逐步走向“数据可分析、可支撑业务决策”。

## 二、这两个多月遇到的问题及解决方案

这两个多月遇到的问题，主要集中在数据口径、接口特性、历史数据处理、维度治理和需求协同这几个方面。很多问题并不是单纯的技术实现问题，而是业务理解、数据来源和系统现状共同作用的结果，因此解决过程中也更多是技术手段和沟通确认同时推进。

### 1. 数据口径不一致

这段时间最常见的问题之一，就是不同来源的数据口径不一致。例如 TikTok API、Excel 导出、积加系统、财务口径之间，在订单状态、退款逻辑、GMV、订单量、运费分摊等方面都存在差异。这类问题如果只从代码角度直接改，很容易出现反复返工的情况。

对应的处理方式主要是先拆分来源，明确每种数据各自代表的业务含义，然后再逐项核对字段来源、时间口径、去重逻辑和状态定义。对于短期内无法统一的问题，会先保留差异说明，再推动业务侧或相关系统方确认最终规则。经过这类处理后，虽然前期花的时间更多，但后续结果会更稳定，也更容易解释。

### 2. 外部平台接口复杂，调试成本高

沃尔玛、Shopee、TikTok 等平台接口在授权方式、token 刷新、字段定义、分页规则和历史数据返回方式上差异都比较大，部分平台还会因为店铺类型、国家站点和权限不同而出现额外差异。这导致接口接入并不是简单开发，而是一个持续调试和验证的过程。

在处理这类问题时，主要采取的方式是优先验证高风险环节，例如 token 获取、授权流程、签名加密和关键接口返回结构；先跑通最小闭环，再逐步扩展订单、产品、财务等完整链路；对于偶发失败、同步异常等情况，则通过增加重试机制和告警方式来提高稳定性。

### 3. 历史数据和增量处理问题

在处理历史数据、补数和日常增量链路时，也出现过数据遗漏、时间窗口覆盖不完整等问题。这类问题在数仓和 BI 工作中比较典型，因为日常链路往往容易只考虑正常增量，而忽略历史补数和边界场景。

针对这部分问题，主要通过补充历史回灌方案、明确任务时间窗口、增加重跑策略和保留调试 SQL 等方式来降低风险。这样做的意义在于，不只是解决当前问题，也让后续遇到类似场景时更容易复用已有经验。

### 4. PID 与 SPU 映射规则不稳定

在 PID 看板推进过程中，比较突出的问题是 PID 与 SPU 关系缺少完全稳定、自动化的规则，部分数据仍然依赖人工导入或人工维护。这类问题直接影响商品维度分析结果，也会给看板稳定性带来影响。

当前的处理方式是先通过维表维护和人工补充映射结果，保证下游看板先可用、先稳定；同时在数仓逻辑上改为优先引用最新维护结果，减少直接依赖单日快照带来的不稳定性。短期来看，这种方式能保证业务使用；长期来看，还是需要继续推动主数据规则的标准化。

### 5. 需求变化和理解差异

从 3 月到 4 月，多项需求都经历了反复确认、UI 调整、范围补充或分阶段拆分的过程。这说明很多需求在刚开始时并不是完全成熟的，而是在推进过程中才逐步清晰。

对应这类问题，当前比较有效的方式是先尽快完成第一版，让业务先用起来，再根据实际使用情况持续修正。因为很多指标口径问题、展示方式问题和操作习惯问题，如果第一版没有真正上线，就很难在口头沟通阶段完全发现。对我来说，这也是这段时间比较深的一个感受：需求第一版要尽快上线，只有真正投入使用后，业务理解和技术理解之间的差异才会逐步暴露出来，后续优化也才会更有方向。

## 三、工作与学习心得

经过这两个多月的工作，我有以下几点比较深的体会。

### 1. 做数仓和 BI，核心是口径统一

很多问题最终都不是通过复杂 SQL 解决的，而是通过明确业务规则、拆解来源差异、统一时间口径和统计口径解决的。对数仓和 BI 来说，真正重要的不是先把逻辑写出来，而是先把规则讲清楚。只有口径统一了，后面的开发、联调和核对才会更顺。

### 2. 数据工作要加强沉淀，不能长期依赖临时排查

这段时间接触了很多接口、看板、RPA、人工导入、历史补数和数据核对工作，比较明显的感受是，如果每次都靠人工临时比对、临时改逻辑、临时问业务，效率会越来越低。后续需要继续加强指标口径说明、常见调试 SQL、维表和映射规则等方面的沉淀，把经验逐步变成标准能力。

### 3. 既要重视交付速度，也要兼顾可维护性

很多需求都带有明显的交付压力，需要尽快上线、尽快支撑业务。但从实际情况来看，如果只追求短期交付，很容易把问题留到后面。比如口径说明不清、历史数据处理方式不统一、维度映射依赖人工经验等，都会在后续逐步放大维护成本。

所以后续在工作中，我会更注意两个平衡点：一是先保证结果可交付，二是在关键逻辑上尽量形成可复用、可解释、可维护的标准化能力。

### 4. 第一版尽快上线，比反复口头确认更有效

从这段时间的实际情况来看，业务需求在刚开始时往往很难一次性定义完整，这其实是正常现象。很多指标口径、使用方式和展示细节，只有在第一版真正上线、业务实际使用之后，问题才会逐步暴露出来。

对我来说，一个比较深的体会是，需求第一版要尽快上线，先让业务用起来，再根据真实反馈持续调整。因为如果第一版迟迟不上线，很多内容都停留在口头沟通阶段，业务理解和技术理解之间的差异其实很难真正暴露和统一。

### 5. 数据工作不仅是开发实现，也要推动问题闭环

这段时间也让我更深地体会到，数据仓库和 BI 工作不仅是开发实现，还需要主动推动需求确认、口径统一和问题闭环。很多问题并不会直接体现在代码里，而是体现在业务定义、数据来源可信度和结果解释方式上。只有把这些问题一起推动解决，数据结果才能真正落到业务场景中。

## 四、小结

总体来看，年后到现在，我的工作重点已经逐步从接口接入和基础数据处理，转向看板建设、指标实现和业务分析支撑。虽然过程中遇到了口径不一致、接口复杂、历史数据处理、维度治理和需求变化等问题，但也逐步积累了更成熟的处理思路。

后续我会继续在数仓和 BI 方向上，加强数据标准化、口径沉淀和稳定性建设，更好支撑业务需求落地。

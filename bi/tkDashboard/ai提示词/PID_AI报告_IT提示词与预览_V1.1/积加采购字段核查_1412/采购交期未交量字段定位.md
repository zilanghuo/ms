## 1. 数据位置与接口
数据位于“采购订单详情”的产品明细，优先使用按仓库拆开的采购订单行：
`data.warehouseProcureItemVos[].procureItemVos[]`

流程：
1. 用站内库存SKU的inventorySku映射ERP SKU。
2. `post_purchase_srm_procure_page(skuList,pageInfo,...)` 查采购单号、状态、关联交货单。
3. `get_purchase_srm_procure_detail(poCode)` 下钻采购订单行，按TK业务与目的/交货仓筛选。
4. `get_purchase_srm_lotNo_detail(code)` 查相关交货单、发货/入库凭证及逐SKU入库日期。
界面应在采购订单/交货单相关页面查看；精确菜单名称与按钮位置本次未实测。

## 2. 真实字段（字段目录确认）
下列相对路径均位于warehouseProcureItemVos[].procureItemVos[]：
| 字段 | 积加字段定义 | 用法 |
|---|---|---|
| id / code / product / sellerSku | 明细ID / 采购订单号 / SKU / MSKU | 关联、去重、按仓分配 |
| arrivalWarehouseName / deliveryWarehouseName | 目的仓库名称 / 交货仓库名称 | 分辨TK、Amazon及履约路线 |
| orderQuantity | 采购数量 | 该采购订单行的采购量 |
| actualQuantity | 已交量 | 已向供应链交货的数量 |
| balanceQuantity | 未交量 | 本任务要接的采购未交数，不等同未入库 |
| delayExpectDeliveryDate | 预计交期 [yyyy-MM-dd] | 当前接口预计日期；需同步更新时间，不自行推断是承诺可售日 |
| expectDeliveryDate | 合同交期 [yyyy-MM-dd] | 单独保留原合同依据 |
| planExpectDeliveryDate | 采购计划带入且不能更改的计划交期 | 计划口径，不能混为当前预计交期 |
| actualDeliveryDate | 实际交期 [yyyy-MM-dd] | 已发生交货日期 |
| deliveryDateChangeMemo | 交期变更备注 | 有值时保留 |
| inboundQuantity / unInboundQuantity | 入库量 / 未入库量 | 与已交/未交分开 |
| lotNoCode | 关联交货单号 | 连到下一步交货、发货和入库凭证 |

交货单：deliveryDate=预计交期；shipmentDate=实际发货日期；warehousingDate=实际入库日期。
lotnoItemVOList[]中product、deliveryQuantity（实交）、quantity（交货量）、poBalanceQuantity、warehousingQuantity、warehousingDate，及发货/入库单号。
inboundDetailsVoList[]有逐SKU inboundDate、inboundQuantity、ibCode。

预计交期为空时，可展示合同交期作为“合同交期/待确认预计”，不能默默更名成当前预计可售。

## 3. 真实历史样例
采购单PO2602064883，状态已完成，包含Amazon与TK仓。示例不是当前在途承诺。
SKU AL-W0199-LL-L 在采购SKU汇总：orderQuantity=23。
分仓行：
- 美亚-大魔王:US_FBA：orderQuantity=14。
- 美国TK-厦门直邮仓：orderQuantity=9。

```json
  "planExpectDeliveryDate": "2026-03-13",
  "expectDeliveryDate": "2026-03-20",
  "delayExpectDeliveryDate": "2026-03-20",
  "actualDeliveryDate": "2026-03-25",
  "inboundQuantity": 9,
  "lotNoCode": "LN2603230066"

```
交货单LN2603230066查得该SKU warehousingQuantity=9、warehousingDate=2026-03-25 14:25:23；入库明细日期2026-03-25，入库单GIB28926032500022317。
采购详情traceId=4c48e262d9aa49868cc3a20d0e8f3a0e。
交货明细traceId=1eb4dde984b5404791b59eac14afd237。

结论：不能把整单/汇总23件全算TK；按TK分仓行核对是9件。本例已交已入库，未交为0。
同时证明存在“TK厦门直邮仓”履约路线，不能统一要求所有TK SKU先运到美国海外仓才算可售；最终可售以实际履约仓的上架及店铺同步为准。

## 4. 当前数据差异与限制
- 站内9/22库存样本：AL-W0199-BLS-M factoryPurchaseUnshippedQty=72；AL-W0199-LL-L=80。
- 积加按这两个精确SKU与invoicesStatusList=[99]查进行中采购，total=0；取消状态筛选后total=5，全部为已完成历史采购单。该查询共5条已取齐，但不是SPU全部SKU的采购全景。
- 上述库存未发货汇总与采购查询没有直接对齐。可能涉及时点、库存字段口径、SKU映射或单据范围；原因尚未证实。不能把库存72/80自动分配到某张历史采购单或虚构交期。
- 该采购单LL-L的采购SKU汇总inboundQuantity=14，而分仓入库为14+9=23；汇总行与分仓量存在差异，须IT对账，不混用两个粒度。
- 同TK行actualDeliveryDate晚于expectDeliveryDate，但isDelayDelivery=false；是否延期需要明确业务规则，不只照搬该布尔标记。
- 站内BLS-M样本物理可用49、同步57；LL-L可用4、同步9，均返回FBA同步差异/oversold_risk。这里只作数据问题披露，不据抽样执行库存动作。
- 本次积加采购字段目录未提供热卖色码字段；站内本次SKU样本亦未返回热卖标记。urgent是加急、listingLevel是商品运营级别，均不能直接等同“热卖色码”。标签来源/规则仍需IT核实或基于SKU销量生成。
- 未核当前所有在途批次的预计可售时间、所有SKU映射、生产系统接入和页面位置。未修改任何系统。

## 5. 给IT的最终字段接入说明
先接积加采购列表→采购详情的分仓SKU行→交货/发货/入库详情。保留采购单号、行ID、仓、SKU、原计划/合同/预计/实际日期以及未交、已交、未入库的不同含义。
热卖标签由站内有依据的规则提供，绑定SKU；采购侧只负责关联交期数量，不凭“加急”生成标签。
报告仅优先展示热卖码，但底层仍对齐全部必要映射和数量。采购未交与站内汇总对账前不得确定接货或放量。

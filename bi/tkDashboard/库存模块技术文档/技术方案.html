库存模块 技术方案

基于《TK库存检查 — 需求文档》《缺补货 — 需求文档》整理，覆盖库存检查看板、缺补货看板两个页面的建设方案。

一、建设目标

  • 统一沉淀库存模块底表，支撑 TK库存检查 与 缺补货看板 两类业务场景。
  • 将多份手工导出数据、平台库存数据、积加接口数据统一落入数仓，形成可复用的数据口径。
  • 支持 PID&SKU、SPU、站点等多个粒度的库存核对、缺货识别、补货建议与导出。

二、需求与产出对照

模块需求核心动作产出
库存检查需求一：PID&SKU 维度看板TikTok 在线商品作为商品范围，关联站点库存、FBT 库存、积加同步库存，计算总库存与异常差异TK库存检查-PID&SKU 看板、导出明细
库存检查需求二：SPU 维度看板基于 PID&SKU 明细底表按 SPU 聚合，重算汇总库存与异常结果TK库存检查-SPU 看板、汇总导出
缺补货需求一至需求四按发货、补货、在途、可售天数等口径汇总，补充站点/店铺/仓库维度判断缺补货看板、导出、自定义分析

三、数据源设计

数据源来源方式主键/关联字段用途
TIKTOK-在线商品文件导入或统一采集PID、SKU、SPU、站点、店铺库存模块商品基础范围表
站点产品库存-自定义导出文件导入SKU、仓库可用量、在途量、采购量、仓别拆分
TikTok.FBT库存-自定义导出文件导入SKU、店铺仓库FBT 在途量、FBT 可用量、自定义导出数据补充
积加-商品管理-可用库存接口拉取PID、店铺、仓别店铺后台实际同步库存口径
发货+补货源数据文件导入 / 过程表SKU、站点、日期缺补货看板的发货、补货、在途与周转口径
待确认点：TikTok.FBT库存-自定义导出 以店铺仓库为口径，但发货+补货报表按 SKU + 站点（美国）统计，三个店铺数据会合并到同一站点结果中。技术上可实现，但需要业务确认该汇总是否符合使用口径。

四、数据流与分层

  1. ODS 层统一接收导出文件与接口原始数据，保留原始字段、原始仓库名称、原始店铺名称。
  2. DWD 层将各数据源按 SKU / PID / SPU 做标准化清洗，统一站点、店铺、仓库映射。
  3. DWS 层沉淀库存检查宽表、发货补货过程汇总表，作为看板核心计算输入。
  4. ADS 层分别输出 ads_tk_inventory_check_sku_1d、ads_tk_inventory_check_spu_1d、ads_tk_replenishment_board_1d 等报表表。
  5. 前端页面通过查询接口读取 ADS 层结果，支持筛选、导出与汇总展示。

五、核心计算口径

5.1 库存检查

  • 我们有的库存：来自站点产品库存、FBT 库存等仓别汇总。
  • 已同步库存：来自积加接口返回的店铺后台实际同步库存。
  • 差异字段：仓别 -1 减仓别 -2，得到仓别 -3 差异。
  • 库存是否异常：差异 > 0 为少同步，差异 < 0 为超卖风险，差异 = 0 为同步正确。

5.2 缺补货

  • 基于发货量、补货量、在途量、可售库存、近期开单/销量口径计算库存健康度。
  • 汇总卡片中已移除“平均加权日销”，保留与业务动作更直接相关的库存、发货、补货指标。
  • 缺货、补货建议、异常识别优先按 SKU 与站点口径输出，便于落地处理。

六、实施方案

阶段工作项说明
阶段一源数据接入补齐 ODS 接入登记，落地在线商品、站点库存、FBT 库存、积加接口
阶段二基础宽表建设完成 SKU 维度库存宽表、SPU 聚合宽表、发货补货过程宽表
阶段三ADS 报表表建设按页面字段生成查询表、导出表、汇总表
阶段四接口与前端联调联调筛选项、列表查询、导出、汇总卡片

七、风险与待确认

  • 部分源数据当前仍是手工导出，时效性与稳定性依赖运营导出流程。
  • FBT 库存与积加同步库存存在字段空置或接口待确认项，需先确认是否可稳定获取。
  • 站点库存、FBT 库存、积加库存的仓库命名不一致，需要统一仓库映射规则，否则差异判断会失真。
  • SPU 汇总场景下，缺失 PID 或 SKU 的记录虽然允许并入 SPU，但需确认 SPU 字段完整性。

# PID板块商务与剪辑开单视频可行性与最终计算逻辑

> 输出日期：2026-08-11  
> 输入规则：`bi/tkDashboard/销售/PID/docs/tkdashboard_PID板块_商务与剪辑开单内容计算规则_2026-08-06.md`  
> 指定视频来源：`ods.ods_traffic_file_tiktok_video_performance_di`  
> 指定剪辑账号来源：`ods.ods_platform_file_tiktok_account_d`  
> 仓库当前已落 DDL 表名：`ods.ods_platform_file_tiktok_account_df`

## 1. 可行性结论

结论：可以打通“视频开单”统计链路，但不能完整覆盖原规则中的“视频和照片开单内容”全部口径。

在仅使用 `ods.ods_traffic_file_tiktok_video_performance_di` 和剪辑账号表的前提下，可计算以下字段：

| 字段 | 可行性 | 说明 |
|---|---|---|
| 商务开单视频 | 可行 | 视频表有 `video_id`、`product_name`、`creator_id`、`sdt`、`gmv`、`attributed_shoppable_video_gmv`，可按 PID、视频 ID、首次正 GMV 业务日去重统计；剪辑账号未命中的视频默认归商务。 |
| 剪辑开单视频 | 可行 | `creator_id` 命中剪辑账号表 `tiktok_uid` 后归为剪辑，按 PID、视频 ID、首次正 GMV 业务日去重统计。 |
| 开单视频合计 | 可行 | 商务开单视频与剪辑开单视频相加；同一 `store_name + pid + video_id` 只能归属一侧。 |
| 剪辑开单内容，含照片 | 不完整 | 当前视频表现表只有 `video_id`，没有 `photo_id`、`content_type` 或照片详情字段，不能覆盖照片内容。 |
| 历史归属生效区间 | 需补约束 | 当前账号表 DDL 为日全量 `df`，字段只有 `tiktok_uid/username/nick_name`，没有 `owner_type/effective_from/effective_to/store_id`。只能按“命中剪辑账号表即剪辑，未命中即商务”的简化口径处理。 |

补充说明：用户指定的账号表名为 `ods.ods_platform_file_tiktok_account_d`，但当前仓库与 DDL 中可检索到的是 `ods.ods_platform_file_tiktok_account_df`。若线上实际表名为 `_d`，需确认字段是否与 `_df` 一致；若一致，逻辑可直接替换表名。

## 2. 能否打通的关键判断

### 2.1 可以打通的部分

1. 视频与 PID 可打通：视频表的 `product_name` 可从商品名称末尾括号解析 PID，现有 DWD 逻辑已使用该方式。
2. 视频与剪辑账号可打通：视频表 `creator_id` 可关联账号表 `tiktok_uid`。
3. 开单事件可打通：视频表存在 `gmv`、`attributed_shoppable_video_gmv`、`video_deal_order_count`，可用正 GMV 判断开单，并用订单数字段做校验。
4. 首次开单日期可打通：若 ODS 每天按 TikTok 后台业务日落快照，可按 `MIN(sdt)` 找到首次正 GMV 日期。
5. PID 页面聚合可打通：最终可沉淀到 `biz_open_video_qty`、`edit_open_video_qty`、`total_open_video_qty` 三个 ADS 字段。

### 2.2 无法完全打通或需补齐的部分

1. 照片无法覆盖：指定视频表未提供照片 ID 与照片 GMV，不能计算“剪辑开单内容”中的照片部分。
2. 账号历史归属不完整：账号表未提供人员归属、生效开始日、生效结束日；如果账号换人，只能依赖账号表每日快照近似追溯。
3. 店铺维度归属不完整：账号表没有 `store_name/store_id`，同一账号跨店铺归属不一致时无法精确拆分。
4. 多 PID 归因存在风险：如果同一视频挂多个 PID 且视频表只给整体 GMV，不能无条件把同一个视频复制统计到全部 PID。
5. 首次开单依赖历史快照：如果历史没有逐日数据，只能从已有最早分区开始判断，不能把首次抓取日等同于真实首次开单日。

## 3. 推荐最终计算口径

### 3.1 时间口径

- 页面日期范围按 `sdt` 闭区间过滤：`start_sdt <= first_open_sdt <= end_sdt`。
- `sdt` 必须代表 TikTok Shop 后台业务日，业务时区为 `GMT-08:00`。
- `publish_time` 是内容发布时间，不作为开单日期；可用于挂车发布日、内容明细展示和排查。

### 3.2 PID 解析口径

从 `product_name` 末尾括号解析 PID：

```sql
REGEXP_EXTRACT(COALESCE(product_name, ''), '[（\\(]([0-9]{18,20})[）\\)]\\s*$', 1)
```

无法解析 PID 的视频，不进入具体 PID 行，建议进入待维护池。若后续人工补齐 PID，应按原始首次开单日期回填，而不是按维护日期统计。

### 3.3 开单判断口径

主判断字段：

```text
COALESCE(attributed_shoppable_video_gmv, gmv, 0) > 0
```

辅助校验字段：

```text
COALESCE(video_deal_order_count, 0) > 0
```

当 GMV 与订单数状态不一致时，仍按 GMV 主口径统计，但建议记录为数据质量异常：

| 场景 | 处理 |
|---|---|
| GMV > 0 且订单数 = 0 | 计入开单，同时标记 `metric_conflict` |
| GMV = 0 且订单数 > 0 | 不计入开单，同时标记 `metric_conflict` |
| GMV > 0 且订单数 > 0 | 正常计入开单 |

### 3.4 商务与剪辑归属口径

推荐以剪辑账号表命中作为归属主判断：

```text
creator_id 命中剪辑账号表 tiktok_uid → editor
creator_id 未命中剪辑账号表 tiktok_uid → business
creator_id 为空 → owner_missing
```

注意：现有 DWD 挂车逻辑曾使用 `account_type` 参与拆分，但当前字段注释与业务表达存在歧义。开单视频口径建议不要仅凭 `account_type = 1` 判断剪辑，除非已由业务确认该字段稳定表示剪辑来源。

### 3.5 首次开单事件

开单事件粒度：

```text
store_name + pid + video_id
```

首次开单日期：

```text
同一 store_name + pid + video_id 首次出现正 GMV 的 sdt
```

若后续退款或归因回写导致 GMV 下降到 0，不自动删除首次开单事件；只有业务人工确认后台纠错时，才通过修正记录调整。

## 4. Doris SQL 逻辑草案

以下为口径草案，用于表达链路，不直接替代生产 SQL。实际落地时需按调度参数、目标 DWD/ADS 字段和分区窗口调整。

```sql
WITH account_snapshot AS (
  SELECT
    tiktok_uid,
    username,
    nick_name,
    sdt
  FROM ods.ods_platform_file_tiktok_account_df
  WHERE COALESCE(tiktok_uid, '') != ''
),
video_daily AS (
  SELECT
    smt,
    sdt,
    store_name,
    REGEXP_EXTRACT(COALESCE(product_name, ''), '[（\\(]([0-9]{18,20})[）\\)]\\s*$', 1) AS pid,
    video_id,
    creator_id,
    creator_name,
    account_type,
    publish_time,
    COALESCE(attributed_shoppable_video_gmv, gmv, 0) AS open_gmv,
    COALESCE(video_deal_order_count, 0) AS open_order_count
  FROM ods.ods_traffic_file_tiktok_video_performance_di
  WHERE sdt BETWEEN '${historyStartSdt}' AND '${endSdt}'
    AND COALESCE(video_id, '') != ''
),
video_account_candidate AS (
  SELECT
    v.store_name,
    v.pid,
    v.video_id,
    v.sdt,
    a.tiktok_uid,
    ROW_NUMBER() OVER (
      PARTITION BY v.store_name, v.pid, v.video_id, v.sdt
      ORDER BY a.sdt DESC
    ) AS rn
  FROM video_daily v
  LEFT JOIN account_snapshot a
    ON v.creator_id = a.tiktok_uid
   AND a.sdt <= v.sdt
),
video_account_match AS (
  SELECT
    store_name,
    pid,
    video_id,
    sdt,
    tiktok_uid
  FROM video_account_candidate
  WHERE rn = 1
),
video_with_owner AS (
  SELECT
    v.*,
    CASE
      WHEN COALESCE(v.creator_id, '') = '' THEN 'owner_missing'
      WHEN a.tiktok_uid IS NOT NULL THEN 'editor'
      ELSE 'business'
    END AS owner_type,
    CASE
      WHEN COALESCE(v.pid, '') = '' THEN 'pid_missing'
      WHEN v.open_gmv > 0 AND v.open_order_count = 0 THEN 'metric_conflict'
      WHEN v.open_gmv = 0 AND v.open_order_count > 0 THEN 'metric_conflict'
      ELSE 'normal'
    END AS data_status
  FROM video_daily v
  LEFT JOIN video_account_match a
    ON v.store_name = a.store_name
   AND v.pid = a.pid
   AND v.video_id = a.video_id
   AND v.sdt = a.sdt
),
first_open_event AS (
  SELECT
    store_name,
    pid,
    video_id,
    MIN(sdt) AS first_open_sdt
  FROM video_with_owner
  WHERE open_gmv > 0
    AND COALESCE(pid, '') != ''
    AND owner_type IN ('business', 'editor')
  GROUP BY store_name, pid, video_id
),
first_open_detail AS (
  SELECT
    e.store_name,
    e.pid,
    e.video_id,
    e.first_open_sdt,
    v.owner_type,
    v.creator_id,
    v.creator_name,
    v.open_gmv,
    v.open_order_count,
    v.data_status
  FROM first_open_event e
  INNER JOIN video_with_owner v
    ON e.store_name = v.store_name
   AND e.pid = v.pid
   AND e.video_id = v.video_id
   AND e.first_open_sdt = v.sdt
),
pid_open_video AS (
  SELECT
    CAST(SUBSTR(first_open_sdt, 1, 6) AS INT) AS smt,
    first_open_sdt AS sdt,
    store_name,
    pid,
    COUNT(DISTINCT CASE WHEN owner_type = 'business' THEN video_id END) AS biz_open_video_qty,
    COUNT(DISTINCT CASE WHEN owner_type = 'editor' THEN video_id END) AS edit_open_video_qty,
    COUNT(DISTINCT video_id) AS total_open_video_qty
  FROM first_open_detail
  WHERE first_open_sdt BETWEEN '${startSdt}' AND '${endSdt}'
  GROUP BY CAST(SUBSTR(first_open_sdt, 1, 6) AS INT), first_open_sdt, store_name, pid
)
SELECT *
FROM pid_open_video;
```

## 5. ADS 字段映射建议

| ADS 字段 | 展示名 | 推荐来源 | 推荐口径 |
|---|---|---|---|
| `biz_open_video_qty` | 商务开单视频 | 视频表现 ODS + 剪辑账号表 | `owner_type = business` 且首次正 GMV 日期落入页面区间，按 `video_id` 去重。 |
| `edit_open_video_qty` | 剪辑开单视频 | 视频表现 ODS + 剪辑账号表 | `owner_type = editor` 且首次正 GMV 日期落入页面区间，按 `video_id` 去重。 |
| `total_open_video_qty` | 开单视频合计 | 视频表现 ODS | `biz_open_video_qty + edit_open_video_qty`；总计行跨 PID 时需再次按 `video_id` 去重。 |

## 6. 与现有最终口径的差异

当前 `PID数据看板最终计算逻辑.docx` 与数仓 DWD 逻辑中，开单视频字段曾使用 `ods.ods_file_trade_tiktok_affiliate_order_di`，按 `product_id + creator_username + content_id` 去重，并用账号表 `username` 区分剪辑/商务。

本次指定改为视频表现表后，口径差异如下：

| 对比项 | 联盟订单口径 | 视频表现口径 |
|---|---|---|
| 内容 ID | `content_id` | `video_id` |
| PID 来源 | `product_id` 直接字段 | 从 `product_name` 解析 |
| 开单依据 | 订单事实 | 视频归因 GMV 或视频成交订单 |
| 剪辑匹配 | `creator_username = username` | `creator_id = tiktok_uid` |
| 照片覆盖 | 可依赖订单 `content_type` 判断 | 当前视频表不覆盖照片 |
| 首次开单日期 | 订单日或内容订单日 | 视频日快照首次正 GMV 日 |

因此，视频表现口径适合回答“哪个视频在 PID 下首次产生归因 GMV”，但不等同于联盟订单事实口径。若经营侧接受“视频归因 GMV 口径”，则可上线；若要求与订单开单事实完全一致，仍需联盟订单表或内容订单明细补充。

## 7. 落地建议

1. 确认账号表正式表名：若线上为 `ods.ods_platform_file_tiktok_account_d`，需补充或确认 DDL；若为当前仓库的 `ods.ods_platform_file_tiktok_account_df`，文档和 SQL 统一使用 `_df`。
2. 确认视频表 `sdt` 是 TikTok 后台 `GMT-08:00` 业务日，且 `gmv/attributed_shoppable_video_gmv` 是单日指标，不是累计指标。
3. 确认 `product_name` 解析 PID 的成功率；解析失败数据进入 `pid_missing` 待维护池，不静默丢弃。
4. 若账号会跨店铺或跨人员变更，建议新增配置维表 `dim.dim_platform_tiktok_account_config` 或类似历史归属表，补充 `store_name/store_id/owner_type/effective_from/effective_to`。
5. 若仍要统计照片，必须补充照片详情 ODS 或改回联盟订单内容明细口径。
6. 生产落地时建议先在 DWD 层沉淀明细事件，再由 DWS/ADS 聚合到 `store_name + pid + sdt`，避免 ADS 直接承载复杂归因逻辑。

## 8. 最终判断

可行，但应按“视频开单”而不是“视频和照片开单内容”命名与验收。

若仅用指定两张表，推荐上线口径为：

```text
按 TikTok 后台业务日，从视频表现表识别首次正 GMV 的视频；
按 product_name 解析 PID；
按 creator_id 命中剪辑账号表判定剪辑，否则归商务；
最终按 store_name + pid + 首次开单日期聚合商务开单视频、剪辑开单视频和开单视频合计。
```

该链路能满足 PID 看板展示和明细追溯的主体需求，但上线前必须明确照片不覆盖、账号历史归属弱、PID 解析失败需人工维护这三项边界。

# tkdashboard PID板块：商务与剪辑开单内容计算规则

> 文档版本：V1.0  
> 制定日期：2026-08-06  
> 适用系统：tkdashboard  
> 适用页面：PID板块  
> 目标字段：`商务开单视频`、`剪辑开单视频`、`开单视频合计`  
> 业务时区：TikTok Shop后台业务时区 `GMT-08:00`，禁止直接使用服务器UTC日期或北京时间归日。

## 1. 需求目标

在tkdashboard的PID板块，按页面选择的日期范围和PID，计算：

1. 商务开单视频数；
2. 剪辑开单内容数（当前页面列名为“剪辑开单视频”，实际包含视频和照片）；
3. 开单内容合计；
4. 每条内容的开单日期；
5. 内容ID与PID的对应关系；
6. PID为空或无法唯一确定时的人工维护流程。

本规则用于“内容首次产生归因GMV”的经营分析，不用于联盟佣金结算、财务结算或奖金池金额核算。

## 2. 页面字段定义

| tkdashboard字段 | 业务定义 | 统计粒度 |
|---|---|---|
| 商务开单视频 | 归属商务的内容中，在所选日期范围内首次出现归因GMV大于0的视频数 | `PID + 日期范围 + 去重内容ID` |
| 剪辑开单视频 | 归属剪辑的内容中，在所选日期范围内首次出现归因GMV大于0的视频和照片数 | `PID + 日期范围 + 去重内容ID` |
| 开单视频合计 | 商务开单视频与剪辑开单内容的合计；同一内容ID不得在商务和剪辑重复统计 | `PID + 日期范围 + 去重内容ID` |

建议前端保留现有列名时增加说明：

- `商务开单视频`：仅视频；
- `剪辑开单视频`：包含视频和照片；
- 更准确的可选列名为`剪辑开单内容`、`开单内容合计`。

## 3. 数据源范围

### 3.1 商务开单视频

数据入口：

```text
TikTok Shop后台
→ 渠道分析
→ 视频和照片
→ 视频列表
→ 已绑定的账号
```

取数范围：

- 内容类型：视频；
- 账号来源：已绑定的账号；
- 排除：账号归属表中在内容发生日归属为“剪辑”的账号；
- 剩余账号的视频归为商务候选内容。

商务账号集合：

```text
已绑定账号集合 - 生效中的剪辑账号集合
```

### 3.2 剪辑开单内容

数据入口：

```text
TikTok Shop后台
→ 渠道分析
→ 视频和照片
→ 视频列表 / 照片详情
→ 已绑定的账号 / 联盟账号
```

取数范围：

1. 已绑定账号中归属剪辑的账号发布的视频和照片；
2. 联盟账号中归属剪辑的账号发布的视频和照片；
3. 同一个内容ID即使同时出现在多个入口，也只保留一条内容主记录。

剪辑账号必须来自可维护的账号归属表，不能在程序中写死。

### 3.3 账号归属优先级

当同一账号或内容同时命中商务和剪辑条件时，采用以下优先级：

```text
人工内容归属 > 生效中的剪辑账号归属 > 商务默认归属
```

因此：只要内容发生日对应账号明确归属剪辑，该内容就不得再计入商务。

## 4. 必须维护的账号归属表

建议表名：`content_account_ownership`。

| 字段 | 说明 |
|---|---|
| store_id | 店铺ID |
| account_id | 达人ID/渠道账号ID，主匹配键 |
| account_handle | 账号名称，仅用于展示和辅助核查 |
| owner_type | `editor`剪辑 / `business`商务 |
| owner_name | 具体人员；无法确定时允许为空 |
| account_source | `bound`已绑定账号 / `affiliate`联盟账号 |
| effective_from | 归属生效日期 |
| effective_to | 归属失效日期，当前有效可为空 |
| maintained_by | 维护人 |
| maintained_at | 维护时间 |

要求：

- 按`account_id`匹配，不优先依赖可能改名的账号名称；
- 必须有生效日期，避免账号换人后历史内容被整体改归属；
- 同一店铺、同一账号、同一天只能有一个有效归属；
- 修改账号归属后，仅按生效区间重算，不覆盖区间外历史。

## 5. 每日快照规范

### 5.1 推荐取数方式

每天按TikTok后台业务日查询单日数据：

```text
查询开始日期 = D
查询结束日期 = D
```

每日保存视频列表和照片详情的原始快照，不允许只保留最新结果。

建议抓取时间：业务日结束且后台数据稳定后执行；如在北京时间运行，必须把后台`GMT-08:00`业务日转换正确，并记录后台返回的业务日期。

### 5.2 快照唯一键

视频建议唯一键：

```text
store_id + snapshot_business_date + content_type + content_id
```

若后台返回商品级明细，则使用：

```text
store_id + snapshot_business_date + content_type + content_id + pid
```

同一天重复抓取必须幂等更新，不得生成重复快照。

### 5.3 快照最低字段

| 字段 | 是否必需 | 说明 |
|---|---:|---|
| store_id | 是 | 店铺 |
| snapshot_business_date | 是 | 后台GMT-08:00业务日期 |
| content_id | 是 | 视频ID或照片ID |
| content_type | 是 | `video` / `photo` |
| account_id | 建议必需 | 达人ID/渠道账号ID |
| account_handle | 否 | 展示、辅助排查 |
| account_source | 是 | `bound` / `affiliate` |
| publish_time | 是 | 内容发布时间 |
| attributed_gmv | 是 | 当日归因GMV |
| attributed_sku_orders | 建议保留 | 当日归因SKU订单数，用于交叉校验 |
| pid_list | 是 | 后台商品字段解析出的PID列表，可为空或多值 |
| raw_payload/raw_file | 是 | 原始数据追溯位置 |
| collected_at | 是 | 实际抓取时间 |

## 6. 开单事件计算

### 6.1 开单判断

用户确认的主口径：

```text
当日归因GMV > 0 → 该内容当日有开单
```

建议同时保存校验字段：

```text
attributed_sku_orders > 0
```

若出现`GMV > 0但订单数 = 0`或`订单数 > 0但GMV = 0`，仍按GMV主口径处理，但写入数据质量异常表供核查。

### 6.2 开单日期

```text
开单日期 = 同一店铺、同一内容ID首次出现当日归因GMV > 0的snapshot_business_date
```

伪代码：

```sql
SELECT
  store_id,
  content_id,
  MIN(snapshot_business_date) AS first_open_date
FROM content_daily_snapshot
WHERE attributed_gmv > 0
GROUP BY store_id, content_id;
```

### 6.3 首次上线与历史回补

禁止把“系统首次抓取日”直接当作历史内容的开单日。

正确处理：

1. 如果可以按历史业务日查询，先逐日回补，再取最早正GMV日期；
2. 如果只能取得累计快照，必须观察到`前一日GMV <= 0 → 当日GMV > 0`才可确定开单日；
3. 系统首次抓取时已经GMV大于0、且没有更早快照的内容，标记为`historical_open_date_unknown`，不得把首次抓取日写成开单日；
4. PID板块历史区间未完成回补前，应明确展示“历史开单日期数据未完整回补”。

### 6.4 开单事件不可因后续退款删除

内容一旦形成有效首次开单事件，后续GMV因退款、归因回写或数据修正下降到0，不自动删除或后移开单日。

如确认为后台纠错，需要写入人工修正记录，保留修正前值、修正后值、原因、操作人和时间。

## 7. 内容ID与PID映射

### 7.1 关系模型

内容ID与PID不是稳定的一对一关系，必须使用桥接表：

```text
content_id × pid
```

建议表名：`content_pid_mapping`。

| 字段 | 说明 |
|---|---|
| store_id | 店铺ID |
| content_id | 视频ID/照片ID |
| content_type | video/photo |
| pid | 商品ID |
| mapping_source | `channel_snapshot` / `affiliate_order` / `manual` |
| evidence_date | 映射证据日期 |
| mapping_status | `confirmed` / `pending` / `invalid` |
| maintained_by | 人工维护人 |
| maintained_at | 维护时间 |

### 7.2 PID解析

当前渠道分析导出没有独立PID列时，从“商品”字段中提取括号内19位商品ID；一条内容可能解析出0个、1个或多个PID。

### 7.3 PID为空处理

补全优先级：

```text
人工确认映射
> 渠道分析当日/历史快照中的PID
> 联盟订单 Content ID → 商品ID
> 待人工维护
```

规则：

1. PID为空的内容仍可形成“内容开单事件”；
2. PID为空时不得直接计入任何具体PID行；
3. 写入`PID待维护池`；
4. 人工补齐PID后，按原始开单日期回填到对应PID历史区间；
5. 不得使用账号ID、达人昵称或相近金额猜测PID；
6. 订单管理缺少Content ID时，不能用订单管理直接补`内容ID → PID`。

### 7.4 多PID处理

如果一条内容绑定多个PID：

1. 若后台返回商品级归因GMV/订单数，只把开单归给当日商品级GMV大于0的PID；
2. 若只有内容整体GMV，无法判断究竟哪个PID开单，不得把同一条开单默认复制到全部PID；
3. 优先用联盟订单的`内容ID + 商品ID`补充实际成交PID；
4. 仍无法确定时进入`多PID待确认池`；
5. 人工允许确认一个或多个PID，但必须保存证据来源。

## 8. 商务与剪辑归属算法

### 8.1 内容主记录去重

对同一店铺、同一内容ID：

```text
人工归属存在 → 使用人工归属
否则账号在内容日期归属剪辑 → editor
否则内容来自已绑定账号 → business
否则 → pending_owner
```

同一内容不得同时归属商务和剪辑。

### 8.2 商务开单视频

满足全部条件：

1. `content_type = video`；
2. 来源为渠道分析视频列表；
3. 账号来源为已绑定账号；
4. 内容发生日账号不属于剪辑；
5. `first_open_date`落在页面日期范围内；
6. PID已经唯一或商品级确认；
7. 按PID和内容ID去重计数。

### 8.3 剪辑开单内容

满足全部条件：

1. `content_type IN (video, photo)`；
2. 来源为视频列表或照片详情；
3. 账号属于生效中的剪辑账号；
4. 账号来源允许为已绑定账号或联盟账号；
5. `first_open_date`落在页面日期范围内；
6. PID已经唯一或商品级确认；
7. 按PID和内容ID去重计数。

## 9. PID板块聚合公式

页面日期范围按开始日、结束日闭区间计算：

```text
start_date <= first_open_date <= end_date
```

### 9.1 商务开单视频

```text
COUNT(DISTINCT content_id)
WHERE owner_type = business
  AND content_type = video
  AND pid = 当前PID
  AND first_open_date BETWEEN 开始日 AND 结束日
  AND mapping_status = confirmed
```

### 9.2 剪辑开单视频

```text
COUNT(DISTINCT content_id)
WHERE owner_type = editor
  AND content_type IN (video, photo)
  AND pid = 当前PID
  AND first_open_date BETWEEN 开始日 AND 结束日
  AND mapping_status = confirmed
```

### 9.3 开单视频合计

```text
商务开单视频 + 剪辑开单视频
```

前提：同一内容已通过归属优先级去重，不会同时出现在商务和剪辑。

页面总计行如果跨多个PID汇总，必须再次按`content_id`去重；不能简单累加各PID行，否则多PID内容可能重复。

## 10. 人工维护与异常池

PID板块至少需要以下异常状态：

| 状态 | 触发条件 | 是否进入具体PID统计 |
|---|---|---:|
| `confirmed` | PID唯一或已有商品级证据 | 是 |
| `pid_missing` | 无PID | 否 |
| `multi_pid_pending` | 多PID但无法判断成交PID | 否 |
| `owner_missing` | 账号无法归属商务/剪辑 | 否 |
| `historical_open_date_unknown` | 首次抓取即正GMV且无历史快照 | 否 |
| `metric_conflict` | GMV与订单数正负状态不一致 | 按GMV主口径计，但需展示异常 |

建议增加“开单内容异常”入口，支持：

- 按店铺、日期、内容类型、异常状态筛选；
- 查看内容ID、账号、首次正GMV日期、GMV、订单数、候选PID；
- 手工选择PID；
- 手工修正商务/剪辑归属；
- 查看原始快照或后台链接；
- 保存操作人、时间、原因；
- 修改后重算对应PID及历史周区间。

## 12. 已知数据质量基线

基于2026-07-01至2026-07-28达人视频样本：

- 726条有归因订单或GMV的视频中，视频ID为空0条；
- PID为空20条，占2.75%；
- 其中5条可通过联盟订单`内容ID → 商品ID`补回；
- 补回后仍有15条无PID，占2.07%；
- 15条未补回内容涉及20个归因SKU订单、GMV 906.15美元；
- 另有6条正GMV视频关联多个PID，不能假设内容ID与PID一对一。

因此系统必须实现PID待维护和多PID待确认，不能在程序中静默丢弃或强制猜测。

## 13. 验收用例

| 编号 | 输入场景 | 预期结果 |
|---|---|---|
| AC-01 | 内容A在D1 GMV=0，D2 GMV>0，D3仍>0 | 开单日期为D2，只计1条 |
| AC-02 | 内容A每天重复出现在快照 | 按内容ID去重，不按快照行数累计 |
| AC-03 | 系统首次抓取时历史内容GMV已>0，无更早数据 | 标记历史日期未知，不把首次抓取日当开单日 |
| AC-04 | 已绑定账号属于剪辑 | 只计入剪辑，不计入商务 |
| AC-05 | 联盟账号属于剪辑 | 视频和照片均可进入剪辑候选 |
| AC-06 | 已绑定账号不属于剪辑 | 视频进入商务候选 |
| AC-07 | 同一内容同时出现在已绑定和联盟入口 | 内容主记录只保留一次，剪辑归属优先 |
| AC-08 | 正GMV内容PID为空 | 形成内容开单事件，但不进入具体PID，进入PID待维护池 |
| AC-09 | 人工补齐PID | 按原开单日期回填对应PID和历史周，不使用维护当天 |
| AC-10 | 内容绑定两个PID、只有整体GMV | 不同时计入两个PID，进入多PID待确认池 |
| AC-11 | 内容绑定两个PID、有商品级GMV | 只计入商品级GMV>0的PID |
| AC-12 | 后续退款导致GMV降为0 | 不自动删除已确认开单日期 |
| AC-13 | 账号归属发生变更 | 只按生效日期影响对应区间，不重写全部历史 |
| AC-14 | 页面选择周区间06/30至07/06 | 按GMT-08:00业务日期闭区间统计 |
| AC-15 | 点击开单视频数字 | 明细数量与汇总数字一致，并能追溯原始快照及PID来源 |
| AC-16 | 页面跨PID总计 | 按内容ID再次去重，不能直接累加PID行 |
